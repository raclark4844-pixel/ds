# Existing campaign runner capture integration

This directory belongs to `ds`. It connects the existing employee Lead Engine to the private website spreadsheet; it is not a new application or repository. The current Vercel employee engine has no linked Git repository. The local engine copies are reference material until the deployment source is confirmed. **These hooks have not been installed in the live campaign runner.**

Apply `vault-outbox.sql` to an isolated copy of the employee engine database first. `saveVaultBatch` must run inside the same database transaction that commits a successful BatchData source page or contact lookup. Adapt Prisma's transaction `$queryRawUnsafe(text,...params)` to the `query` interface (SQL text comes only from this module; all values are parameters). Package this module with `src/lib/data-vault/records.ts` or import it through the controlled shared server package; never fetch code at runtime.

For each core page, map the existing normalized property fields: `externalRef -> providerId`, `address1 -> address`, `address2 -> unit`, `city`, `state`, `postalCode`, `propertyType`, `yearBuilt`, `estimatedValue`, `ownerOccupied`. Omit missing/blank optional values. Save every valid returned property, including properties not enrolled after campaign filtering, so purchased information is not discarded. Use one frozen observedAt timestamp from response receipt and a stable requestId based on job ID and page cursor. One batch holds at most 100 records. No owner/customer/organization choice comes from provider data.

For contact enrichment, capture the verified input property address (including unit from the stored Property record) plus the adapter's normalized `contacts` array, only when `matched` is true. Capture all returned phone/email values and restriction flags. Never interpret fresh data as consent or remove existing CRM suppression records. The employee enrichment adapter currently omits unit from its lookup contract: resolve that before enabling captures for multi-unit addresses. Unknown/ambiguous matches must be held for review.

The sender `scripts/deliver-private-results.ts` uses an explicitly scoped `LEAD_ENGINE_DATABASE_URL`, `BATCHDATA_VAULT_SENDER_ENABLED=true`, and `BATCHDATA_VAULT_CUSTOMERS_JSON`. The JSON maps verified engine customer IDs to `{integrationId,secret}`. The website independently binds each integration ID to one organization through `BATCHDATA_VAULT_INTEGRATIONS_JSON`. Configure only the two approved Demore businesses initially. Never infer a mapping from a similar company name.

Run the sender with the existing scheduler; it does not create a scheduler or buy data. Retry delivery of the durable saved batch, not the provider request. Accepted receipts become `accepted`; transient failures retry up to six attempts; configuration/conflict failures become `review`. A lost acknowledgment resends the same requestId and payload. The website treats that as a replay, not a new row. No campaign sends a notification or outreach message through this connection.

Release remains blocked until actual source-page and enrichment hooks are installed in the verified active runner, tested with synthetic provider responses end-to-end, and the production customer-to-organization bindings and owner are verified. Do not claim automatic campaign capture from the presence of the receiving endpoint alone.
